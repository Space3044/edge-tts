# Agent Note: Trancy 额度是带时间的观测，不是实时余额

Status: implemented

## Problem

用户反馈剩余额度不对，刷新也不变。账号刷新仅请求 `/1/user/profile`，不读字幕额度；
面板却把无观测的账号当作每日 5 次，用昨天的余额显示今天的状态，并把失效、冷却账号
计入总余额。`day_used` 是网关成功调用次数，既不包含站外使用，也无法识别上游缓存免扣额。
旧的列表自愈 UPDATE 还会清掉真实调用计数，且并发成功请求会相互覆盖计数。

## Decision

额度只表达字幕请求实际观测到的信息，账号凭据状态独立表达：

- `quotaStatus` 为 `unknown / observed / stale / exhausted`。`quotaRemaining=-1` 表示未知；
  过 UTC 日的观测不再作为当天余额，旧 0/0 缺失响应头数据也按未知投影，GET 不修写数据库。
- UI 显示「上次观测」及时间，不用默认 5 减调用次数推算；汇总只包含当前可调度账号，
  未知账号单列。`captionAvailable` 表示允许尝试请求，不保证生成成功或有余额。
- 刷新按钮叫「检查登录」，明示不查询额度；HTTP 200 内的探测失败也展示失败。
  面板可见时每分钟、窗口重新激活时重读列表；列表响应和浏览器读取均禁止缓存。
- AI 成功响应分别保存有效的 limit/remaining，缺失 remaining 会使旧余额失效。
  json3 不更新 AI 观测、不增加 AI 计数，也不受 AI exhausted_until 限制。
- daily-limit 拒绝保存上限和零余额，停泊到 UTC 零点；普通 403 不按耗尽处理。
  当天观测为零但没有明确拒绝时仍可尝试一次：历史实测的 header limit 与免费每日文案不一致，
  不能仅凭它证明全天额度已耗尽。UTC 零点只是本地允许重试时间，不承诺上游实际重置。
- 日调用次数用 SQLite CASE 表达式原子累加。额度本身保留最后完成响应的观测值，
  不对上游计费或并发额度预留作保证。最多尝试 3 个账号不等于整个池子已经耗尽。
- profile 只有明确的 `message=ok, data=null` 判 token 无效；非 JSON、错误体或缺少用户 ID
  都是软失败，避免把暂时上游错误显示为永久登录失效。

不引入新列，不修改远端数据，不以生成字幕探测额度。公开网页脚本检查没有找到可确认的
独立额度查询接口；若后续取得真实接口证据，可以用同一观测字段保存其结果。

## Alternatives considered

- **继续显示 `5 - day_used` 并在跨天重置为 5**：随时有一个数字且不用新接口，
  但站外使用、上游缓存、会员差异都会让它错误，用户当前反馈正来自把估算当实数。
- **每次刷新调用字幕接口获取额度响应头**：可以获得新观测，但会生成字幕并可能消耗有限额度；
  没有证据证明某个视频永远命中缓存，不能作为余额查询实现。
- **只改文案，保留旧余额**：改动小，但跨天旧余额、json3 误停泊和并发计数丢失仍会出现。

## Consequences

用户能分辨已观测与未知额度，登录检查也不会暗示更新余额。代价是一些账号显示未知，
无法提供全池精确实时总额度；要补足必须先验证独立查询接口。UTC 日界仍是本地约定。
每日计数防丢失不等于账号额度预留，也不保证并发请求只消费一个名额。

## Testing

`node scripts/verify-trancy-quota.mjs` 用内存 SQLite 执行真实 SQL，覆盖跨天、未知、0/0 遗留数据、
部分及缺失响应头、12 个并发增量、json3、刷新不改变额度、拒绝分类和三次尝试预算。
同脚本执行真实前端渲染函数及刷新失败处理，验证汇总不包含失效/冷却账号和假定的 5 次。
现有 gateway、frontend-redesign、code-hygiene 和 README 校验继续运行；浏览器使用本地虚构账号验证。
